## Purpose
The sync core, module `github.com/Busnes-app/kydrive-desktop/core`. `kydrive-sync` runs one per user; `kydrive-sync ctl METHOD [JSON]` calls it for debugging.

## Ownership
- `api/` — REST client for KyDrive, including device signing and vault transport.
- `vault/` — native vault keyring enrollment, witnessed history, encrypted revisions and editor sessions.
- `link/` — loopback + PKCE linking.
- `engine/` — state DB (`db.go`), pull (`pull.go`), push (`push.go`), conflict/evict rules (`engine.go`).
- `cmd/kydrive-sync/` — `account.go` owns identity hashing/credential migration; `accounts.go` owns the account registry and per-request RPC routing. The daemon owns: keyring, socket, JSON-RPC service `Core`, watcher, poll loop.

## Local Contracts
- **Pass:** `Engine.Sync` lists workspaces, then per workspace pulls (feed from the cursor; full snapshot on first sync, an unknown folder, or 410) and pushes (scan, moves by inode/file ID, new folders, settled uploads with `expected` revision and `mtime`, then deletes). `Engine.Poll` pulls only. The daemon polls every 45 s and on wake or address change; scans at start, every 10 minutes and after fsnotify activity on Windows/Linux. macOS uses the periodic scan instead of kqueue (one descriptor per file); server polling remains 45 s. Choose, Unlink, ConfirmDeletes and Pause cancel the active pass and take priority over queued passes. Local scan/feed/snapshot/evict loops, reverse directory sweeps, move/delete/reader accounting, retry bookkeeping and content checks observe cancellation; a staged-file eviction finishes that file before yielding so its name and bytes stay accounted for. A push that fails locally (an unreadable folder), or a lost-access evict that cannot finish (retried next pass), fails that workspace only; the pass goes on to the others and reports the error. One core runs per state directory (an exclusive `lock` file, taken before the socket).
- **Downloads** go to `.kydrive-*.tmp` beside the target, are checked against size and server `digest`, get the server mtime, and are renamed in only if the target is still free or still the unchanged synced copy. A failed one is kept in `retries` and tried again each pull, as is a file the pull cannot write or move locally (open elsewhere, no permission, destination occupied); that never stops the pass, and each is announced once. While the daemon runs, each retry backs off (45 s doubling to 30 min). Only KyDrive's own JSON 403/404 means a download is gone. After a transport, incomplete-body or 5xx download failure, probe the authenticated workspace API: a failed probe stops the pass before further downloads; a reachable API keeps the file in retries and continues unrelated work. Such failures share one warning until a download succeeds; digest/local failures retain per-file warnings. A reader workspace's scan failing (an unreadable folder) fails that workspace only, as a push does. A server folder move refused locally, a server folder blocked by a local file (synced once freed, with a snapshot for what was skipped below it) and a server removal that cannot finish locally (a name-less retry) wait in `retries` the same way. A feed entry the record already holds while the local copy is missing is not downloaded: the push sends the local move or delete. The same holds in a snapshot the feed forces (an unknown folder, 410); only a restore snapshot (cursor -1: a new binding, an evict, refused deletes) brings missing copies back. A snapshot does not fetch a file whose failed download is backing off. A server file whose name a local folder, link or special file holds waits in retries and is never opened; a server folder whose name a file or link holds waits the same way. A file moved in from another chosen workspace first removes its old source copy through eviction (preserving edits), before any destination record replaces its identity, including ignored/invalid/case-twin skips. Failed source cleanup defers destination recording and retains independently owned retries; a downloadable destination then downloads fresh here; it never moves this workspace's own file. Retries and their in-memory backoff belong to `(workspace, item ID)`, so dropping the destination cannot discard unfinished source cleanup. Retry bookkeeping receives the active context, stops between entries and keeps each completed wait/next pair together; cancellation leaves other workspaces and persistent retries untouched. A server file or move whose name is still recorded as another item (renamed or removed on the server, its change later in the pull) waits silently in retries until that item's own change frees it, never making a conflict; when that item itself waits in retries to move (a swap), its copy, if unchanged and matching its digest, is evicted and downloads again in its new place; a changed one is announced and waited for. On a case-insensitive disk the very same name is such a record, not a case twin. A skipped record (a case twin) gives way to a move onto its path. Two folders that swap names: the one holding the name moves aside to `.kydrive-move-<id>` and on from there in its own retry. An item recorded while another item's record still holds its path (the server replaced a file with a folder of that name, or the reverse) is recorded under a placeholder path (`\x01blocked-<id>`: no server name holds a control character), so the other's removal still finds it. A server file or folder under a local link (a synced folder moved elsewhere, a link left), and that folder itself, wait in retries with their records untouched, so moving the folder back takes the server's versions. An item the server renames into a name this computer skips leaves its old place as a server removal does; a case twin instead waits in retries, its synced copy kept and recorded where it is, since the other item may be on its way out. Upload failures are announced once until the file next uploads.
- **Paths stay inside the workspace folder.** Every server name passes `serverName` before it becomes a path (a refused one is skipped under a `.kydrive-refused-<id>` placeholder that never touches disk), and `Engine.abs` refuses a non-local path or one with a symlinked ancestor (a Windows junction counts). Use `abs` for every path built from DB or server data.
- **Changed** means size, mtime, inode/file ID or change time differs from what the last sync recorded, or the item is `stale`. Linux/macOS use filesystem ctime; Windows uses NTFS ChangeTime. A missing/unknown change time requires a content check, including after upgrading the state schema: matching bytes are re-recorded, never accepted without hashing. Sample identity/change time before hashing, downloading into place or reading upload bytes (from the open upload handle on Windows), and carry that sample into the record. Reader scans use the same content check before listing edits. A same-size/mtime rewrite waits for its change time to settle before hashing/uploading. Before a local copy is replaced by a download or deleted by an evict, its content is also checked against the recorded digest, so an edit written in place that kept size and mtime is kept (a conflict copy, or Unsynced); a copy whose content is the recorded digest is the synced copy whatever its metadata (a folder copied back from another disk). A changed file whose content is still the synced one (copied back from another disk) is recorded again, not uploaded. A changed file whose server revision is the one recorded is a pending upload, never a conflict. A file uploads once its mtime is at least `Settle` old; a future mtime never waits.
- **Conflict:** local change meets a newer server revision, or the server refuses an upload (409): the local file becomes `<name> (conflict from <device> <YYYY-MM-DD>).<ext>` (``<>:"|?*`` in the device name become `-`), uploads as a new file, and is listed as an issue. Identical content is adopted instead.
- **Evict** (lost access = workspace gone from the list or KyDrive's own JSON 403/404 on feed/snapshot; unchoose; server removal; wipe): synced unchanged copies are moved aside, checked again and deleted (so an editor's save landing meanwhile is kept), `.DS_Store`/`Thumbs.db`/`desktop.ini` are deleted, everything else moves to `Unsynced/<workspace folder>/`. A file or unreadable folder that cannot go does not stop the rest; each file's record leaves with the file, the rest stay so the evict can run again. A whole-workspace evict sets the cursor to -1 before it starts, so a workspace that stays chosen (lost access retried, a crash) re-snapshots to restore what was removed; an unchoose drops the binding anyway, leaving what could not go on disk unsynced, with a warning.
- **Revoke:** `401 device_revoked` stops syncing, replaces the keyring item with a pin-only revoked record (token field `-`, no signing key), and wipes only when `wipe` is true. The held pin (or known legacy absence) survives restart; failed retirement writes keep reauthentication blocked until regular-pass keyring recovery succeeds. A wipe is recorded (config `wipe`) before it starts and resumed at the start of every pass, without credentials, until it completes; `Link` and `Unlink` refuse while it is unfinished. A symlink, junction or Finder alias encountered by a wipe is kept with its records and returns an explicit unfinished-wipe error: restore the folder or remove the link before resuming. Wipes never inspect or delete through a link target. `Unlink` with `RemoveFiles` records the same wipe before it starts, then completes the unlink even when a file cannot go yet. A plain 401 (or no keyring item at start) is `signed_out`: nothing is deleted, and the keyring is read and the server retried with backoff (45 s doubling to 30 min), warning once. `Link` for a retained revoked/signed-out selection routes through `SignIn`, requiring the retained server, identity and TLS pin while keeping selector/root/bindings/files; explicit `AddAccount` still rejects that identity. `SignIn` relinks the same server through the browser keeping the bindings; recorded complete KyIdentity issuer/sub/org_id must match exactly. Only legacy accounts compare the immutable local `user_id`, even when the username changed; a missing or different legacy ID is refused and the new credential revoked. Only a link with no recorded ID falls back to its case-insensitive recorded username (`user`); with neither, sign-in is refused. A successful authenticated workspace query on a server with `GET /api/drive/device` records its validated account identity before syncing. Complete hosted claims are authoritative and need no local `user_id`; a legacy credential can learn its first complete hosted tuple from this authenticated route. Once recorded, hosted claims cannot change or downgrade; partial claims always fail. Legacy-only replies still require the recorded local ID (bounded response; a 401 uses the normal revoke/wipe path). A 404 keeps legacy behavior, while every other lookup failure stops the pass. Tokens remain only in the keyring. An approval that lands after `CancelLink` or `Unlink` is revoked, not activated; once saving starts there is nothing left to cancel. `CancelLink` ends a `Link` or `SignIn` waiting for the browser, as do `Unlink` and a new `Link` or `SignIn` (a shell started again cannot see the old one). `SignIn` waits for an unfinished wipe, as `Link` does. Unlink calls `DELETE /api/devices/self` (best effort) then deletes the keyring item.
- **Not a delete:** a recorded item the scan does not list but whose path still holds something (a link or special file in its place, a folder moved to another disk with a link left behind) or has a link above it is never trashed; the link itself is listed once as skipped. A regular file or folder answering only under a case variant of the name (a case-insensitive disk) is a delete. On macOS a Finder alias (a bookmark file) at a synced folder's name is such a link too, and that folder's server changes wait in retries as for a link. A workspace folder that is itself a link (moved to another disk, a link or junction left in its place) is not synced at all; the pass reports it for that workspace only.
- **Large-delete guard:** a push that would delete more than half of a workspace and more than 20 items, or whose workspace folder is missing, waits for `ConfirmDeletes`; refusing re-snapshots and restores the files. A missing writable workspace folder arms the guard before the pull, which would otherwise recreate it; confirmed deletes still pull first, so files added on the server since are not trashed with their folder. A confirmed guard with nothing left to delete is cleared. While deletes wait, the workspace's other changes still pull and push; held deletes stay held, whatever the server adds, until confirmed or none remain. Before trashing a folder (the server trashes everything in it), the push reads the feed since its pull; a folder with anything changed under it waits for the next pass. Folder trash sends that pull’s workspace cursor as JSON `head`, so the server atomically refuses a changed live subtree with 409. On 409 its synced record and any delete confirmation stay, and the next pass pulls before deciding. Old servers reject the unknown field: only a 400 followed by a 404 from the device-account route permits a legacy request without `head`; never downgrade a 409, a known modern server or a failed/malformed probe. The feed check remains for old servers; its final request window is not atomic.
- **Skipped (listed, never synced):** ignored names (`~$*`, `.~lock.*`, `*.tmp`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, both directions so ignoring never reads as a delete); case-only duplicates on Windows/macOS (first by feed order, snapshot sorted by name); Windows-invalid names on Windows, and on Windows a new name shaped like a short (8.3) name, such as `REPORT~1.TXT`, where something already answers to it; names the server refuses.
- New workspace folders are named after the workspace with `/\<>:"|?*` and control characters as `_` (a reserved Windows name becomes `Workspace`), and use names absent from both current bindings and the sync root (numbered names fit 255 bytes), including retained files/directories from an unlinked account; collisions get ` (2)` and existing paths are never implicitly adopted. Test candidate names with `Lstat` as well as the enumerated spellings, respecting native Unicode normalization; only not-exist means free, and every other lookup error is returned. `Unsynced` is reserved. Reader workspaces only pull; files added or edited in one are listed once each as a `readonly` issue ("read-only workspace; not uploaded"); a synced copy deleted in one is restored by a snapshot, so it is never a pending delete when the user becomes an editor.
- **Upgrade:** `Status.Version` is the core's release (`version` in `main.go`, checked against the tag by the release job). `Quit` exits an idle core (refused during a pass or a waiting link, holding the work lock until the exit) so a shell bundling a newer release can start its own (the macOS shell asks launchd to start the agent's). It exits 0, so neither the launch agent (`SuccessfulExit=false`) nor the systemd unit (`Restart=on-failure`) restarts it by itself.
- TLS policy is the `core/go.mod` default `godebug fips140=on`, shared across the
  daemon's one HTTP client for linking, APIs and file transfers. Preserve normal
  chain/hostname verification and reject all redirects. Never weaken the runtime
  policy to repair an endpoint: correct its certificate chain. TLS failure must
  preserve credentials, bindings and local work. docs/TLS-KEY-POLICY.md owns operator migration.
- **TLS leaf pinning** follows KyDrive-server `internal/api/tls_pin.go` and mirrors KyDrive-for-Android `TlsPin.kt`; `api/testdata/tls-pin-v1.json` is its golden vector, copied byte for byte. `api/tlspin.go` checks the leaf SPKI in `VerifyConnection` with one `http.Client` per pin (only a handshake with an `https` proxy the transport's `Proxy` chose skips it; a host spelled unlike its SNI, such as a trailing dot, is still checked). Linking pins the redemption's leaf with `identity_key`; an unpinned session pins the leaf of its first 2xx (floor = now) and learns the key once from `GET /api/drive/device`, write-once, only over the pinned leaf. A mismatch makes one credential-free `GET /api/devices/tls-pin` over system trust, serialised per session; `accept` requires the observed leaf, the lowercase host, ±24 h, `issued_at` above the floor, a new leaf and a valid signature. `SignIn` on a pinned computer passes the session's `Pins` to `link.Link`, which makes a credential-free `Client.Reach` before opening the browser and redeems over the same pins, so only the pinned leaf or a signed successor (saved by the same compare-and-swap) is reached; anything else returns `errSignInPin` (Unlink, then Link again), with nothing credential-bearing sent. `keepPin` carries the held floor and identity key into the new credential and refuses (revoking it) a reply carrying another key. A computer with no pin, and every `Link`, trusts on first use. The daemon's `sessionPins` saves with compare-and-swap bound to the token, so unlink or re-link during the fetch wins; then one retry. Anything else is `api.ErrPinChanged`, which the engine reports as `ErrSignedOut` (nothing deleted). An ended session sends nothing.
- **Device signing** follows KyDrive-server `internal/api/devicesig.go`; `api/testdata/device-signing-v1.json` is its golden vector, copied byte for byte. `link.Link` generates a P-256 key before redeeming the code and sends its SPKI as `publicKey`. A `Client` with a `Key` signs every request it sends with its token, buffering the body so the digest and Content-Length match what is sent; the signed origin is `Base` canonicalised, so tests that interpose a proxy reroute the transport (`env.via`), never `Base`. The keyring item (`credential.go`) is space-separated: the token; the key as std base64 PKCS#8 DER (`-` for none); then, once pinned, the TLS pin, the identity key (`-` until learned) and the pin's floor. One item, stored and deleted together. A bare token is a computer linked before signing and stays unsigned. The key is a software key; a non-exportable platform key is not implemented.
- Linking accepts `https` servers, or `http` on loopback for development. Every approved link clears previous workspace bindings, cursors and item/retry records under the work lock before saving and activating new credentials; files remain untouched and workspaces must be selected afresh. A refused approval preserves existing bindings. Platform names are `windows`, `macos`, `linux`.

- **Origin identity:** `accountID` uses `serverOrigin` for both the server tuple member and the local-user namespace’s origin. Host case and default ports cannot create another account; KyIdentity issuer/sub/org_id remain byte-for-byte. Keep the persisted server spelling for legacy keyring-source lookup, and finish an earlier cleanup marker before committing a new credential migration. Canonical credential identity never renames the original storage selector or root. Unlink deletes through the original pointer, then atomically retains the canonical identity while clearing the active server, including when migration could not read the credential.
- **Accounts:** `Accounts` lists non-secret account metadata; `AddAccount` approves a separate browser link; `RemoveAccount` unlinks the requested account. Existing RPC methods accept optional `AccountID`; omission retains the old primary installation, or the only added account, and refuses ambiguous selection. Selectors belong to each request, never global daemon state. New account databases are `accounts/<first-identity-hash>/state.db`, roots are `~/KyDrive Accounts/<first-identity-hash>`, and the old primary database/root stay in place. Storage selectors remain stable if an old server later supplies KyIdentity identity. New linking never writes an origin-keyed credential. Migration copies the complete old item, commits its selector and cleanup marker atomically, then deletes the source; retries preserve the same token, key and pin. Re-adding a removed account finds its retained daemon by the current canonical `account_id`, then reuses the original storage selector, database and root, including after local-user to KyIdentity migration; retained files are not adopted as synced copies.
- **Identity ownership:** the manager serializes Link, AddAccount and SignIn approvals through its existing reservation. All approval paths check the same canonical identity against other registered links before resetting bindings or publishing credentials; a duplicate revokes only its newly issued device. Unlinked state may retain identity metadata but owns no active credential slot. A pending migration marker reserves its source slot until deletion and marker cleanup complete, including after unlink, so another approval cannot overwrite an item awaiting retirement.
- **Replacement commit:** canonical `account_id` identifies the account; `credential_slot` identifies its physical keyring item and takes precedence over the canonical fallback. Replacements use independently owned `account:<identity>:<random>` slots (identity-less legacy links use fresh `pending:<random>` slots). Before writing, `credential_migration` records the new slot as abandoned-stage cleanup; atomic `SetConfig` switches the pointer and changes that marker to the previous slot. A precommit failure leaves the exact previous credential/session/pin and bindings intact, revokes only the new approval, and retains cleanup on keyring failure. Restart and regular passes finish recorded cleanup; same-identity recovery must not move a committed physical pointer back to the canonical slot. Pending physical source slots reserve their canonical identity until cleanup completes.
- **Keyring availability:** a keyring availability failure that prevents saved-credential recovery leaves the account `signed_out` while RPC and other accounts remain available. Signed-out backoff retries migration, including pending source cleanup, before loading credentials. Browser activation installs the token, signing key, pin and idle state immediately after its durable pointer commit; retirement/marker failures retain the cleanup marker and do not fail that committed activation. Regular passes retry cleanup for known sessions and explicitly unlinked accounts, even while sync is paused. A replacement must finish an existing cleanup marker before storing another credential, so pending source ownership cannot be lost. Incomplete identity, conflicting target credentials and state-store failures remain errors; retry never activates the old credential after a migration conflict. A startup credential that could not be read has unknown pin state, so `SignIn` waits for recovery to read it successfully; it never treats unread pin state as a known unpinned legacy link.
- **Server compatibility:** device-token/device-account responses may carry `issuer`, `sub`, `org_id`; issuer/sub must be complete together, and org_id cannot downgrade to local identity. Older servers supply local `user_id`; a server that never supplies an immutable identity supports only the primary Link path. Hosted deployment must supply KyIdentity claims before advertising tenant-qualified desktop sync.

- The native vault path uses the linked device's signed, pinned API client and a separately
  pinned witness. The `Vault` RPC returns account fingerprints, vault invitations and
  generations. Keep plaintext, editor grants and decryption keys inside the native host.

## Child DOX Index
- `vault/` owns the native vault client and editor session contract.
